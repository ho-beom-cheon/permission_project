# P1 사용자 SSO소속·신규 권한 상태 전이

2026-09-03. `6da19e5` 이후 작업 트리 기준. 두 서브에이전트가 사용자 조회와 권한 전이를 나누어 구현하고, 주 에이전트가 API·화면·기존 저장 호환·통합 검증을 수행했다. 원본 `C:\arisuinfo`는 읽기만 했으며 원본 DB에 접속하지 않았다.

## 이번 변경

| 영역 | 구현 내용 | 경계 |
|---|---|---|
| 사용자 SSO소속 | 사용자→SSO사업소·부서 저장, 대응표 선택 UI, 낙관적 버전 검사 | 기존 사용자 프로필과 권한의 조직 ID를 바꾸지 않음 |
| 담당자 조회 | 별도 `/api/colleagues`, 사용자명·SSO부서명 LIKE, 본부/사업소별 서버 범위 | 최신 권한 이력 EXISTS 조건은 후속 작업 |
| 본부 판정 | `CM087/BONBU` 하위 코드의 사용 여부와 **코드명**을 SSO사업소 코드와 비교 | 그룹·상위 코드의 표시 기간은 원본 판정 조건이 아님 |
| 조회 인가 | `SYSTEM_AUTH/AUTHORITY/DIRECTORY_LOOKUP`, 해당 권한 보유 시 포털 링크 표시 | 기능 정의만 자동 등록하며 관리자에게도 자동 허용하지 않음 |
| 신규 권한 신청 | 서버가 v2 지정, 실제 DIRECT PENDING 이력 기록, 권한별 대기 제한 | 기존 v1 대기가 있으면 같은 사용자·조직·시스템의 신규 신청 차단 |
| 신규 승인·반려 | 자신의 최신 PENDING sequence 확인 후 APPROVED/REJECTED 기록 | 승인 기간은 처리일~9999-12-31, 반려 시작·종료는 처리일 |
| 신규 변경 신청 | 미보유 대상 한 개 선택, 승인 시 같은 조직·시스템의 현재 유효 직접 권한 회수 | 일괄 심사에서는 사용자·조직·시스템별 회수를 먼저 한 번 수행 |
| 저장 호환 | 버전 누락은 v1, 기존 요청·baseline 구조 유지, v2 PENDING 복원 후 심사 | 과거 요청에 임의 신규 사건이나 날짜를 만들지 않음 |

SSO소속이 없거나 대응표가 비활성이면 조회를 거절한다. 비본부는 대응된 업무 사업소만 조회하며 다른 사업소 요청을 거절한다. 본부는 사업소를 지정하거나 전체 범위를 조회할 수 있다. 본부 여부를 기존 `HQ` 조직이나 관리자 계정으로 추정하지 않는다. 기존 관리자 전체 사용자 관리 API는 별도 관리 권한으로 유지한다.

조회 화면은 `colleagues.html`, 소속 관리는 `management.html`의 ‘사용자 SSO소속’ 항목이다. 새 조회 기능을 사용하려면 활성 SSO 대응표와 사용자 소속을 등록하고, 권한 관리에서 `DIRECTORY_LOOKUP` 기능을 명시적으로 허용해야 한다. 실제 SSO 로그인 연계는 아직 구현하지 않았다.

v2 PENDING/REJECTED를 실제 이력에 연결하므로 과거 미래 시작 승인 건이 이후 날짜에 되살아나지 않는다. 위임 권한 판정은 기존 경로를 유지한다. 조직 이동 후 승인은 거절하고 반려는 신청 당시 조직에 기록한다. 관리자 직접 부여·회수로 최신 PENDING을 덮어쓰는 동작도 차단했다.

## 검증

- 자동 테스트 **109개 통과**, 실패·오류·건너뜀 없음. 이전 92개 대비 SSO 조회 6개, 원본 권한 전이 7개, legacy 호환 2개, HTTP 버전·기간 계약 2개 추가.
- 파일 DB 재개방: 새 저장 키가 없는 상태에서 기존 영역 유지, SSO소속 저장·복원, v2 PENDING 복원 후 승인, 신규 journal 순번 유지.
- 강제 실패: 조직 대응·SSO소속·신청·처리 이력·DB 내용·revision 동시 롤백.
- 권한: 미래 승인 억제, 반려 후 과거 승인 부활 방지, 변경 대상/일괄 순서, 최신 신청 충돌, 조직 이동, v1 기간·복수 대상 유지, 클라이언트 버전 선택 차단.
- SSO: 사업소 범위 우회, 관리자 우회, 미등록·비활성 대응, 본부 하위 코드명/사용 여부, LIKE 대소문자·와일드카드, 저장 버전·인가·CSRF.
- 별도 메모리 DB의 18081 서버에서 신청→반려와 처리 당일 기간, 소속 사업소 조회 및 복합 검색, 사용자 SSO소속 선택·저장을 확인했다. 테스트 코드의 합성 공통코드 식별자를 30자·대문자 제약에 맞춰 수정한 뒤 전체 테스트를 다시 실행했다.
- JavaScript 구문 및 `git diff --check` 통과. 포털의 담당자 조회 링크를 확인하고 검증 탭·18081 서버를 종료했다. 기존 8080 서버는 재시작하거나 변경하지 않았으며 로그인 응답 200을 확인했다.

실행: `mvn -o '-Dmaven.repo.local=C:\workspace' --batch-mode --no-transfer-progress test`

로그: `target/migration-third-test.log`, `target/surefire-reports`. 검증은 합성 데이터만 사용했다.

## 남은 차이와 다음 우선순위

1. 원본 SSO사업소·부서와 권한 조직 식별자의 명시적 연결 계약 확정. 이를 선행해 담당자 조회의 최신 권한 이력 EXISTS 및 원본 `100→200` 보정을 적용한다.
2. 복원 가능한 과거 신청·처리와 처리 시각 불명인 직접 부여·회수를 구분해 전체 이력 조회를 연결한다. 현재 마스터 명칭 결합과 반려·회수 사유 정정도 남아 있다.
3. 관리자 직접 재부여의 현재 유효 승인 차단, 개별 회수 사유·처리일 종료 규칙을 원본에 맞춘다. 이번 변경은 PENDING 덮어쓰기 차단과 CHANGE 회수 기간을 우선 적용했다.
4. AI 신청과 연결 AB 권한 규칙, 복수 시스템 경계, 실제 SSO 및 Oracle 동등성 시험을 진행한다.
