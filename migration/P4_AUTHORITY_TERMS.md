# 4단계 권한 신청 이용약관 이관 계약

## 원본 계약

- 약관 마스터의 원천은 `TN_CM_UTZTN_TRMS`, 사용자 동의 이력의 원천은 `TN_CM_UTZTN_TRMS_AGRE`다.
- 권한 신청 화면은 신규 권한의 시스템을 최초 등장 순서로 중복 제거한다. AI 신청으로 자동 선택된 AB·CY 권한도 신규 행이면 각 시스템 약관 확인 대상에 포함된다.
- 신청 화면의 조회 조건은 시스템, 약관 유형 `01`(개인정보처리방침), 상태 `02`(게시중), 사용 여부 `Y`다. 필수 동의 여부가 `Y`인 약관 중 로그인 사용자가 같은 약관 순번에 `Y`로 동의한 이력이 없는 시스템만 팝업을 연다.
- 기존 동의의 재사용 키는 사용자와 `UTZTN_TRMS_SEQ`다. 버전과 시행 기간은 저장·표시되지만 원본 신청 조회에서 최신 버전 선택이나 시행 기간 필터로 사용되지 않는다. 같은 순번의 버전·본문 수정은 기존 동의를 재사용하고, 새 순번은 다시 동의한다.
- 약관은 유형, 정렬 순서, 필수 여부, 버전, 순번 순으로 표시한다. 시스템 반복 순서는 신규 신청 권한에서 시스템이 처음 등장한 순서다.
- 필수 항목은 모두 `Y`여야 다음 시스템 또는 제출로 진행할 수 있다. 선택 항목은 `N`도 동의 결정으로 저장한다. 게시·사용 중인 필수 약관이 없는 시스템은 동의 없이 진행한다.
- 동의 이력과 사용자 정보, 담당 지역, 권한 신청은 한 트랜잭션으로 저장된다. 권한 신청이 실패하면 같은 호출에서 먼저 저장한 동의 이력도 롤백된다.
- 원본 서버는 화면이 보낸 약관 순번과 동의 여부를 저장하며 필수 동의, 시스템 일치, 게시 상태를 다시 검증하지 않았다. 이관 서버는 최종 권한 집합으로 계획을 다시 계산하고 제출 결정과 일치하는지 검증해야 한다.

## 원본 데이터 추출과 입력 형식

- [export_authority_terms_ai_cy_mo_ab.sql](sql/export_authority_terms_ai_cy_mo_ab.sql)은 `AI`, `CY`, `MO`, `AB` 약관 마스터를 변경하지 않고 조회한다.
- 결과의 별칭을 유지해 다음 JSON 객체로 내보낸다.

```text
{
  "terms": [원본 약관 조회 결과]
}
```

- 각 행은 `seq`, `systemId`, `typeCode`, `version`, `title`, `body`, `statusCode`, `enforcementStart`, `enforcementEnd`, `requiredFlag`, `sortOrder`, `useFlag`를 가진다.
- 원본 시행일 `YYYYMMDD`와 승인 과정에서 ISO로 변환된 `YYYY-MM-DD`를 모두 입력할 수 있다. 서버는 두 형식을 명시적으로 파싱해 같은 날짜로 저장하며, 존재하지 않는 날짜·다른 형식·종료일이 시작일보다 빠른 행은 전체 import 전에 거부한다.
- `sortOrder`는 필수 정수다. 원본 `NULL`을 0으로 추정하지 않으며, `NULL`이 발견되면 원본 담당자가 값을 확인한 뒤 다시 추출해야 한다.
- 제목, 본문, 버전, 날짜, 정렬 순서와 플래그를 자르거나 바꾸지 않는다. 시행 시작·종료일의 DB `NULL`은 빈 문자열로 추정하지 않고 JSON `null`로 보존한다. 제목·본문·버전은 원본 필수 문자열로 검증한다.
- 실제 약관 제목·본문·버전·기간 seed는 원본 소스에 없다. 운영 DB에서 승인된 읽기 전용 추출 결과를 받을 때까지 실제 데이터 이관은 대기 상태다.

## 관리자 이관 절차

1. 승인된 원본 조회 환경에서 추출 SQL을 실행한다.
2. 결과 건수와 시스템별 전체·필수 건수를 원본 담당자가 검토한다.
3. `/authority-requests.html`의 관리자 약관 이관 영역에서 JSON 파일을 선택한다.
4. 화면의 시스템별 전체·필수 건수와 일부 행 형식을 실제 파일과 대조한다.
5. `AUTHORITY_UPDATE` 권한이 있는 관리자가 `POST /api/admin/authority-terms/import`를 실행한다.
6. 서버는 전체 행을 먼저 검증하고 한 상태 경계에서 upsert해야 한다. 한 행이 잘못되면 부분 반영하지 않는다.

파일 선택과 미리보기는 저장 작업이 아니다. 이 저장소에는 실제 운영 본문이나 예시 가짜 약관을 넣지 않는다.

## 신청의 두 단계 제출

1. 사용자가 최종 권한을 선택해 신청 버튼을 누르면 화면은 `POST /api/me/authority-requests/terms-plan`에 `authorityIds`를 보낸다.
2. 서버는 최종 권한 시스템을 기준으로 `requiredSystems`, `items`, `unconfiguredSystems`를 반환한다. `items`는 최소한 `termSequence`, `systemId`, `title`, `body`, `required`를 제공한다.
3. 화면은 시스템 목록, 약관 미설정 시스템, 필수·선택 약관을 표시한다. 선택 권한이 바뀌면 이전 계획을 폐기하고 다시 조회한다.
4. 사용자가 필수 항목에 모두 동의한 뒤 다시 제출하면 화면은 신청 본문에 `termDecisions: [{termSequence, agreed}]`를 포함한다.
5. 서버는 저장 직전에 약관 계획을 다시 계산하고 결정 목록과 일치하는지 확인한 뒤 동의 이력과 권한 신청을 같은 상태 경계로 저장해야 한다.

화면과 백엔드 import·plan·제출 검증은 준비되어 있으며, 실제 원본 약관 데이터 반입 전까지 운영 데이터 이관은 대기 상태다.

## 후속 동의 이력 이관

단계 7에서 `TN_CM_UTZTN_TRMS_AGRE`의 기존 사용자 동의 이력을 별도 import 경로로 추가했다. 원본 테이블에 PK가 확인되지 않으므로 일곱 원본 컬럼이 모두 같은 행도 `duplicateOrdinal`로 구분해 보존한다. 추출 형식과 관리자 절차는 [P7_AUTHORITY_TERM_AGREEMENT_IMPORT.md](P7_AUTHORITY_TERM_AGREEMENT_IMPORT.md)를 따른다. 실제 승인 원본 JSON 적재는 계속 대기 상태다.
