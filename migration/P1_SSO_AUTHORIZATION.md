# P1 사용자별 SSO 인가 전환

2026-09-03. `6da19e5` 이후 작업 트리 기준. 기존 사용자에게 자동으로 새 인가 방식을 적용하지 않고, 관리자가 사용자별로 전환할 수 있도록 구현했다. 원본 `C:\arisuinfo`는 읽기만 했고 원본 DB는 사용하지 않았다.

## 변경한 동작

| 구분 | SSO 인가 활성 사용자 | 기존 방식 사용자 |
|---|---|---|
| 실제 권한 | 현재 SSO사업소·부서에 연결된 최신 직접 이력 → 승인·기간·권한 마스터 활성 검사 | 현재 로컬 조직의 기존 직접·위임 판정 유지 |
| 신규 신청 | v3, 신청 당시 SSO 두 코드 저장. 동일 SSO범위·권한별 대기/현재 유효 승인 차단 | 기존 v2 신청 |
| 승인·반려 | 요청에 저장된 SSO범위의 최신 PENDING 확인 후 해당 범위에 기록 | 저장된 v1/v2 처리 규칙 유지 |
| 변경 승인 | 사용자·시스템·신청 SSO범위의 현재 유효 직접 권한만 회수. 일괄 처리는 범위별 한 번 회수 후 승인 | 기존 버전의 회수 범위 유지 |
| 관리자 직접 부여 | 현재 SSO범위의 중복 대기·현재 유효 승인 차단 후 직접 부여 | 기존 관리 부여 규칙 유지 |
| 관리자/일괄 회수 | 현재 SSO범위의 최신 승인 직접 이력만 처리 | 기존 로컬 조직의 회수 정책 유지 |
| 위임 | 대상 또는 원천이 SSO 인가 사용자이면 새 위임 거절. 해당 위임의 효력도 인정하지 않음 | SSO 전환 사용자와 무관한 기존 위임 유지 |

같은 로컬 조직 ID 안에서 SSO A→B로 이동하면 A 권한은 B에서 유효하지 않다. A 신청을 B 이동 후 승인해도 승인 기록은 A에 남는다. 반대로 현재 사용자 소속으로 기존 요청을 다시 해석하지 않는다. 과거 SSO대응이 비활성돼도 확인된 원래 범위의 심사는 가능하며, 실제 효력은 활성화된 현재 SSO대응에서만 판정한다.

## 활성화와 저장 호환

`management.html`의 **SSO 인가 전환**에서 사용자를 선택하고 활성 여부를 저장한다. 먼저 사용자 SSO소속과 필요한 직접 권한 이력의 SSO 연결을 준비한다. 준비하지 않은 권한은 활성화 후 사용 권한으로 인정되지 않는다. 기본 `admin`의 활성화에는 현재 SSO범위의 유효한 직접 관리자 권한 연결이 필요하다.

새 저장 키 `sso-authorizations`는 사용자별 `enabled`, `version`을 저장한다. 키가 없는 이전 저장소와 설정하지 않은 사용자의 기본값은 false다. 수정은 `expectedVersion`으로 충돌을 검사한다. 비활성으로 되돌리는 것은 기존 로컬 조직 기준의 권한 판정을 다시 적용하는 명시적 관리 작업이다.

- `GET/POST /api/admin/sso-authorizations`: 권한 관리 조회/수정 인가, POST CSRF 적용.
- 기존 AuthorityRequest에 선택적 SSO사업소·부서 필드 추가. v3는 두 코드가 필수이고 v1/v2 생성자와 저장 데이터는 계속 읽을 수 있다.
- 남은 v3 신청은 모드를 비활성화해도 v3로 처리한다. 같은 사용자·로컬 조직·시스템에서 기존 버전의 대기 신청과 새로운 버전이 섞이는 신청은 거절한다.
- 소속·SSO대응·이력 연결·모드 변경이 활성 사용자에게 영향을 주면 권한 버전을 갱신한다. API 인가 재평가, 포털 갱신, 이전 일괄 회수 미리보기 충돌에 반영된다.
- 명시 연결 이력의 등록시각과 순번이 서로 다른 로컬 조직에서 같아 최신 건을 결정할 수 없으면 인가는 권한 없음, 변경 처리는 충돌로 처리한다. 임의 순서를 만들지 않는다.

## 원본과의 대응

원본 `src/main/resources/mappers/arisuinfo/cm/auth/auth/authUsrMapper.xml:826–853`의 현재 SSO사업소·부서 제한과 최신 전체 상태 선택 후 승인·기간 판정을 공통 resolver에 반영했다. `insertAuthUsrProc:368–425`와 `UsrMngServiceImpl.java:342–349,451`의 선택 신청 행 소속 유지에 맞춰 v3 처리 범위를 고정했다. 신규 중복 신청은 원본 권한·SSO범위의 최신 상태를 기준으로 한다.

기존 로컬 마스터 활성 검증, 사용자 비활성 검사, 기본 관리자 필수 권한 회수 방지는 유지했다. 원본 위임의 SSO 저장 계약을 확인하지 못한 상태에서 기존 로컬 위임을 SSO 직접 권한으로 인정하지 않는다.

## 검증

- 자동 테스트 **143개 통과**, 실패·오류·건너뜀 없음. 이전 126개 대비 공통 SSO 인가 7개, v3 신청·심사 4개, 관리자/일괄 회수 및 인가 API 5개, 파일 DB 재개방 1개 추가.
- A/B 동일 권한 분리, 이동 후 원래 범위 승인·반려, 범위별 일괄 CHANGE, 오래된 신청 충돌 및 모드 해제 뒤 v3 처리.
- 현재 범위의 직접 부여 중복 차단, 직접/일괄 회수의 다른 SSO범위 보존, 소속 변경 후 이전 미리보기 거절.
- 기존 로그인 요청의 즉시 인가 재평가, 위임 원천/대상의 SSO 전환 조합 차단, 연결 누락·비활성 대응·최신 순서 충돌에서 기존 권한으로 돌아가지 않음.
- 모드 관리 API 인가·CSRF·버전 충돌, 관리자 활성화 전 필수 권한 검사. 모드·연결·소속 변경의 권한 버전 갱신.
- 파일 DB 재개방 뒤 모드·A/B 두 개 v3 대기 신청 보존 및 각각 승인. 강제 실패 시 모드·요청·연결·journal·DB·revision 동시 롤백.
- 별도 18081 메모리 서버에서 관리 화면의 사용자별 활성화 저장, 신규 신청의 당시 SSO 범위 표시를 확인했다. 동일 로그인 세션·로컬 HQ 조직을 유지한 채 A→B 소속만 바꾼 뒤 기존 관리 화면 접근이 차단되는 것을 확인했다.
- JavaScript 구문, 변경 공백, UTF-8·대체 문자와 기능 대응표 경로 검증을 통과했다.
- 같은 세션에서 B의 동일 권한 신규 신청이 별도로 저장되고 A/B 두 신청의 소속 표시가 유지됨을 확인했다. 검증 탭·18081 서버는 종료했으며 기존 8080 로그인 응답 200을 확인했다. 기존 서버는 재시작하지 않았다.

실행: `mvn -o '-Dmaven.repo.local=C:\workspace' --batch-mode --no-transfer-progress test`

로그: `target/migration-fifth-test.log`, `target/surefire-reports`. 검증은 별도 메모리/임시 파일 DB의 합성 자료만 사용했다.
