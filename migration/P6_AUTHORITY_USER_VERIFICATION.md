# 단계 6 권한·사용자 이관 통합 검증

## 검증 범위

단계 1~5에서 구현한 권한 마스터·분류 import, 연계 권한 계획, 시스템별 신청 약관, 신청자 정보·담당지역, 권한별 원자 신청을 하나의 사용자 흐름으로 확인했다. 단계 6에서는 다음 범위를 함께 검증했다.

- 권한 마스터와 분류 import가 `AI`, `AB`, `CY`에 더해 `MO` ID와 분류·권한 연결을 검증하고 보존한다.
- 권한 신청 심사 목록과 처리는 동일한 사업소 범위를 적용한다. 기본 `admin`과 기존 `CM087/BONBU` 정책으로 판정한 본부 사용자는 전체를 조회한다. 비본부 사용자는 기존 신청은 로컬 조직 ID, v3 신청은 심사자와 신청 당시 SSO 사업소·부서를 각각 현재 활성 조직 대응표로 변환한 로컬 사업소가 같은 건만 조회·처리한다. SSO 부서가 달라도 같은 로컬 사업소이면 허용하며, 대응이 없거나 비활성이거나 로컬 사업소가 비어 있으면 범위에 포함하지 않는다.
- 범위 밖 신청 번호가 일괄 처리에 섞이면 처리 전에 전체를 거부하고 신청·권한 상태를 변경하지 않는다.
- 단계 1~5의 상태와 신규 SSO·약관·신청 상태를 파일 DB에서 닫고 다시 열어 복원한다. 실패 경계에서는 상태와 감사·신청·권한 이력이 함께 롤백된다.
- 관리자 import API의 권한과 CSRF, 신청 API의 인증·검증, legacy 저장 상태의 누락 필드 복원 호환을 자동 테스트로 확인했다.

## 실행 결과

- Maven 전체 회귀 테스트: **202개 통과**, 실패·오류·건너뜀 없음.
- 격리된 로컬 파일 DB를 닫고 다시 열어 재시작 복원을 확인했고, 같은 소스로 실행 패키지를 빌드해 기동을 확인했다.
- 브라우저 smoke에서 `viewer`로 로그인해 `AUTH_CONTENT_MANAGER`를 선택했다. 약관 계획 API가 실제 약관 원천 데이터가 없는 시스템을 `unconfigured`로 반환하는 것을 확인한 뒤, 신청자 정보와 담당지역을 포함한 batch 제출이 성공하고 권한별 신청이 `PENDING`으로 저장되는 것을 확인했다.
- 심사 범위 통합 테스트에서 legacy 로컬 조직 격리, 서로 다른 SSO 부서의 동일 로컬 사업소 허용, 다른 로컬 사업소와 비활성 대응 제외, 다른 범위가 섞인 일괄 처리의 전체 거부와 무변경, `admin` 전체 조회를 확인했다.

이 결과는 합성 로컬 데이터와 로컬 인증으로 수행한 구현·회귀 검증이다. **실제 원본 권한·분류·약관·사용자 데이터는 적재하지 않았다.** 따라서 원본 데이터 건수와 값의 운영 동등성이나 실제 SSO 연동 완료를 뜻하지 않는다.

## 남은 운영 이관 대기

1. **기존 약관 동의 이력 실제 적재**: 단계 7에서 원본 사용자별 agreement 이력의 완전 중복을 보존하는 추출·검증·관리자 import 경로를 추가했다. 승인된 실제 JSON을 확보해 원본 건수와 값의 동등성을 검증해야 한다.
2. **운영 사용자·조직 데이터**: 실제 사업소·부서·담당지역·사용자와 `AUTH_USR_DTLS`, `CM008` 직급 코드 추출본을 확보해 Directory와 신청자 정보에 적재해야 한다.
3. **승인 원본 export**: 권한 마스터·분류·연결·약관 본문의 승인된 JSON export를 전달받아 현재 import API로 적재하고 원본 건수·식별자·사용 여부를 대조해야 한다.
4. **실제 SSO**: 운영 로그인 속성으로 사용자 SSO 사업소·부서를 수신하고, 승인된 조직 대응표와 본부 코드로 인증·인가·심사 범위를 종단 검증해야 한다.

임의 권한명, 분류, 약관 본문, 사용자 소속, 직급 코드는 생성하지 않는다. 위 원천 자료가 승인되기 전까지 해당 항목은 운영 이관 대기로 유지한다.
