# ARISUINFO 공통 영역 이관 실행 계획

작성일: 2026-09-03

이 계획은 현재 대응표와 구현 현황을 바탕으로 작성했다. 이번 계획 작성에서 원본 전체 재분석, 기능 구현, 테스트 재실행은 하지 않았다. 실제 완료 상태는 검증 근거를 확보한 뒤 갱신한다.

## 1. 목표와 기준선

목표는 ARISUINFO 공통 업무를 HTML/JSON 기반 프로그램으로 전체 이관하고, 원본의 입력·조회·저장·승인·팝업·출력 및 연계 동작을 검증하는 것이다.

| 지표 | 현재 기준선 | 관리 방법 |
|---|---:|---|
| 원본 조사 파일 | 749개 | 원본 해시와 추가 의존성을 추적 |
| 원본 화면 | 147개 | 화면별 기능과 대상 화면 연결 |
| 매핑 선언 후보 | 383개 | 클래스·메서드 조합과 실제 호출 확인 |
| SQL 구문·조각 | 493개 | include·동적 조건·부수 효과 확인 |
| 원본 컨트롤러 | 68개 | 부분 대응 32개, 미대응 36개 |
| 동등성 검증 완료 | 0개 | 기능별 검증 후 상위 단위로 집계 |

32/68은 부분 대응 비율이며 전체 이관 완료율이 아니다. 기존 65개 자동 테스트 통과는 2026-09-02 문서의 기록이다. 테스트 파일 연결만으로 원본과의 동등성을 인정하지 않는다.

원본 소스는 읽기 전용으로 참조한다. 원본 INFO DB의 실제 데이터는 복사·추출·이관하지 않고 데이터·스키마를 수정하지 않는다. 신규 저장소와 직접 만든 가상 데이터를 사용한다. 외부 연계는 승인된 별도 시험 환경에서 검증한다.

## 2. 우선순위와 진행 순서

| 순서 | 단계 | 선정 이유 | 진입 조건 | 단계 종료 기준 |
|---|---|---|---|---|
| P0 | 추적 체계·기준선 정리 | 누락과 완료 여부를 기능 단위로 판단 | 현재 소스·대응표 확보 | 68개 컨트롤러의 작업 배정, 첫 구현 묶음의 상세 대응·검증 시나리오 확정 |
| P1 | 권한·사용자·조직·메뉴 | 모든 업무의 접근 범위와 이력 처리에 영향 | 해당 원본 기능 분석 완료 | 내부 규칙 검증 완료, SSO 관련 잔여 항목 별도 식별 |
| P2 | 공통코드·기준정보·공통 선택 기능 | 후속 화면·배치의 코드·일정·참조 관계를 제공 | 필요한 P1 조직·권한 규칙 확정 | 기준정보 규칙·계산·참조 정책 검증 완료 |
| P3 | 게시판·도움말·사용자 업무·포털 | 기존 부분 구현을 업무 흐름 단위로 완성 | 관련 P1·P2 규칙 확정 | 대상 화면·API·첨부·이력의 내부 기능 검증 완료 |
| P4 | 과업·이슈·배치·운영 이력 | 미대응 운영 업무를 구현하고 처리 흐름 연결 | 전용 권한·근무일·저장 계약 확정 | 내부 운영 흐름과 실패·재처리 시나리오 검증 완료 |
| P5 | 외부 연계·리포트·운영 저장소 통합 | 외부 시스템과 실제 출력·저장 결과를 검증 | 시험 환경·연계 규격·해당 업무 구현 확보 | 연계별 시험 증적 및 저장소 검증 확보 |
| P6 | 전수 동등성 확인·인수 준비 | 누락·임시 대체·검증 공백을 해소 | 업무별 구현·연계 검증 완료 | 전체 범위에 완료 근거 연결, 미대응·미검증 항목 해소 |

P0에서 모든 세부 분석을 마칠 때까지 구현을 멈추지 않는다. 전체 범위의 작업 배정을 먼저 끝내고 P1부터 분석된 기능 묶음 순서로 진행한다. 기능마다 구현 직후 API·화면·저장 검증을 수행하며 P6에 검증을 몰지 않는다.

운영 저장소 설계와 외부 연계 규격 조사는 P0부터 함께 진행할 작업 흐름이다. P5는 조사 시작 시점이 아니라 실제 통합 검증 단계다. 특정 연계 환경이 준비되지 않아도 독립적인 내부 기능 개발을 계속한다.

## 3. 단계별 작업

### P0 — 기능 추적과 최초 작업 묶음 확정

1. 원본 해시·조사 범위와 현재 소스를 비교해 목록의 유효성을 확인한다. 동적 호출, 매핑 조합, SQL include와 범위 밖 의존성을 수동 보완한다.
2. 32개 부분 대응과 36개 미대응을 모두 작업 묶음에 배정한다. 화면·공통 스크립트·Mapper만 있는 기능도 별도 항목으로 추가한다.
3. 기능 단위 대응표 `migration/feature-mapping.csv`를 새로 작성한다. 원본 컨트롤러 개수와 업무 기능 개수는 별도 집계한다.
4. 최초 상세 분석 대상으로 사용자·조직 변경, 권한 신청·심사·위임·회수, 메뉴·기능 권한을 선정한다.
5. 기존 테스트를 격리된 가상 저장소로 재실행하고 현재 실패 여부를 기록한다. 미완료 브라우저 시나리오를 업무별 검증 항목에 배정한다.
6. 기존 매핑 생성 도구는 `PARTIAL`/`NOT_MAPPED`와 완료 0개를 생성하는 구조이므로, 상세 대응표의 수동 검증 근거를 덮어쓰지 않도록 집계·생성 책임을 분리한다.

산출물: 기능 대응표, 업무별 분석 목록, 검증 기준선, 저장소·연계 의존 목록. 이 파일명들은 앞으로 만들 산출물이며 현재 작성 완료를 뜻하지 않는다.

### P1 — 권한·사용자·조직·메뉴

| 작업 묶음 | 주요 작업 | 검증 사례 |
|---|---|---|
| 사용자·조직 | 전체 필드, 사업소·부서·지역·담당업무 관계, 사업소별 관리 범위, 동시 수정 | 다른 사업소 조회·수정 차단, 조직 이동 후 기존 신청 처리, 비활성 사용자 접근 |
| 권한 이력·위임 | 원본 이력 식별·최신 판정, 승인·반려·회수, 위임 원천·기간·중복·시스템 범위 | 같은 권한의 이력 경합, 위임 원천 회수, 기간 경계, 중복 승인 |
| 일괄 처리 | 원본 선택 범위·사유·부분 실패 정책과 구현 대조 | 일부 대상이 변경된 일괄 요청, 전체 롤백, 감사·알림 일관성 |
| 메뉴·프로그램 | 원본 컬럼·트리 검색·양방향 매핑·삭제 영향·출력 요구 | 권한 변경 후 메뉴와 API 일치, 하위 기능 정리, 직접 API 호출 |
| 인증·모니터링 계약 | 원본 로그인·오류·조직 식별·내 정보·접속 항목 분석, 로컬 인증과의 차이 기록 | 로그인 실패·만료·사용 중지, 서버 범위, SSO 식별자 매핑 |

주요 대상: `AuthorityRequestService`, `AuthorityRevocationService`, `EffectiveAuthorityService`, `AuthorizationCatalog`, `DirectoryService`, `LocalAccountService`, `SessionMonitorService` 및 관련 컨트롤러·화면.

완료 판정: 원본 내부 규칙별 결과·거부·이력·감사를 검증한다. SSO 연계 검증이 남은 기능은 `WAITING_EXTERNAL`로 유지하며 상위 업무 전체를 완료 처리하지 않는다.

### P2 — 공통코드·기준정보·공통 선택 기능

1. 공통코드 표시 플래그별 선택 조건, 그룹·상세·하위 삭제 정책, 출력·엑셀 요구를 보완한다.
2. 은행·지점·기관·매개변수·코드값·기본문자의 전체 필드, 검색, 중복·삭제·참조 관계를 대조한다.
3. 휴일 연간 생성, 음력, 근무일, 월별 일정 계산을 원본 규칙에 따라 구현한다. 경계일·윤년·연도 변경 사례를 검증한다.
4. 미대응 `CgStdInfoMng`, `CsCdMng`, `HgyeSmokArvMng`은 원본 분석으로 업무 의미·입출력을 먼저 확정한 뒤 구현한다. 이름만으로 동작을 추정하지 않는다.
5. 출력문구의 사업소 적용 범위와 보고서 전달 규칙을 확정하고, 실제 보고서 출력은 P5와 연결한다.
6. 주소·코드·사용자 선택의 검색·반환값·선택 취소·권한 범위를 정의하고 호출 화면에 연결한다. 외부 주소 서비스가 필요하면 해당 연계만 별도 추적한다.

완료 판정: 원본 규칙에서 도출한 가상 입력에 대해 조회·계산·삭제 결과가 일치하고, 선택 결과가 호출 화면과 저장 API에 정상 반영된다.

### P3 — 게시판·도움말·사용자 업무·포털

1. 게시판 전체 필드·자동 번호·공지 팝업·메인 롤링·PDA 구분을 보완하고 기존 조회수 구현과 원본 증가 조건을 대조한다.
2. Q&A 상태·메뉴 분류, 시스템·유형별 약관 적용·동의 조건을 구현한다. 게시판 시스템 분류와 실제 접근 권한을 구분해 검증한다.
3. 업무별 첨부 연결, 현재·과거 버전 접근, 삭제·보존 규칙을 확정한다. 파일 요청과 PDA 이미지 업로드도 원본 사용처와 연결한다.
4. 도움말 구분·검색·통계·팝업과 개인 일정 코드·달력 표현을 보완한다.
5. 업무 알림, 처리 이력, 관리번호 이력을 구현한다. 권한 알림 외에 필요한 발생 업무를 목록화하고 P4·P5 생산 이벤트와 연결한다.
6. 원본 메인·메뉴 목록·로그 스트림·초기화·관심 메뉴·공통 프레임의 동작을 현재 포털과 대응시킨다. SSE 등 전달 방식의 필요성은 원본 사용처 분석으로 결정한다.

완료 판정: 조회→작성→변경→첨부→이력→포털 반영을 사용자별로 확인한다. P4·P5에 의존하는 알림·출력은 잔여 상태를 유지한다.

### P4 — 운영 업무 확대

1. 과업·이슈의 상태 코드·검색·출력·오류 팝업·전용 업무 권한을 보완한다.
2. 배치 마스터, 휴일 지연 실행, 스케줄러, 실제 업무 실행과 처리일정 집계를 구현한다.
3. 배치 테스트 진입점의 목적과 권한을 분석하고 신규 구조에서 필요한 검증·운영 동작으로 대응한다.
4. 엑셀 다운로드 로그, 서식 이력, 연계·전자결재·전자고지·발송 이력의 조회·상태 모델을 구현한다.
5. 외부 요청·응답과 내부 이력을 연결하고 실패·시간 초과·중복 요청·재시도·재기동 시 복구 규칙을 정의한다.

완료 판정: 가상 작업에서 실행·지연·실패·재처리·중복 방지·이력 보존을 확인한다. 시험용 대역으로 통과한 외부 호출은 실제 연계 완료와 구분한다.

### P5 — 외부 연계·출력·저장소 통합

| 작업 흐름 | P0부터 준비할 내용 | 통합 검증 내용 |
|---|---|---|
| SSO | 식별자·조직·인증·로그아웃·오류 규칙, 시험 계정·환경 | 로그인·조직 반영·만료·사용 중지·로그아웃 |
| SMS·메일·UMS | 요청·결과·상태·재시도·시험 수신 대상 | 발송·실패·중복 방지·결과 이력 |
| 전자결재·전자고지·REST·전문 | 송수신 규격, 콜백, 인증, 오류·재처리 규칙 | 상태 전이·위변조/중복 요청 처리·장애 복구 |
| 리포트·QR·VoiceEye | 서식·필드·인코딩·출력문구·라이브러리·시험 라이선스 조건 | 출력물의 값·배치·페이지·코드 판독 결과 |
| 공통 기반 | BaseController·MessageUtil·메시지·예외·ID 발급·공통 스크립트의 실제 책임 | 신규 공통 처리와 각 호출부의 결과 일치 |
| 운영 저장소 | 대상 DB 결정, 원본 구조 대응, 키·제약·인덱스·이력·버전 설계 | 정규화 저장, 동시 처리, 롤백, 백업·복원, 성능·장애 |

저장소는 P1의 사용자·권한 모델부터 업무별로 적용해 재작업을 줄인다. 최종 스키마가 미확정이면 H2 구현에서 저장 계약을 분리하고 미확정 항목을 기록한다. 기존 로컬 합성 데이터의 유지·변환 규칙도 명시한다. 원본 운영 데이터의 이관은 하지 않는다.

완료 판정: 해당 기능의 실제 시험 연계 결과와 별도 저장소 검증을 확보한다. 환경·규격·라이선스가 없는 항목은 필요한 조건과 다음 행동을 적고 대기 상태로 관리한다.

### P6 — 전수 확인과 인수 준비

1. 147개 화면, 383개 매핑 후보, 493개 SQL/조각과 추가 발견 항목을 기능 대응표에 연결한다. 중복·재사용 조각도 사용처와 판단 근거를 남긴다.
2. Nexacro 공통·프레임·스크립트의 초기화, 검증, 팝업 반환, 오류, 출력 책임이 누락되지 않았는지 확인한다.
3. 원본 화면·API·SQL에서 도출한 기대 결과와 신규 구현의 결과를 가상 데이터로 대조한다. 원본 실행이 불가능한 경우 정적 분석 근거와 시험 환경에서 추가로 확인할 항목을 구분한다.
4. 업무별 권한·동시 수정·일괄 처리·재시작·첨부·감사 및 핵심 브라우저 흐름을 통합 검증한다.
5. 예상 데이터량·동시 사용자·응답 시간 기준을 확정한 뒤 성능·복구 시험을 수행한다. 기준 없이 운영 적합 판정을 하지 않는다.
6. 실행·업무·개발·DB 문서와 이관 현황을 최종 동작에 맞춘다. 배포 절차와 복구 절차를 준비하되 실제 운영 배포는 별도 실행 단계로 둔다.

완료 판정: 범위 내 모든 기능에 검증 근거가 있고 미대응·미검증·외부 대기가 해소돼야 한다. 필요한 외부 시험을 수행하지 못한 항목은 전체 완료 판정에서 제외하지 않고 미완료로 남긴다.

## 4. 최초 실행할 작업 묶음

| 순서 | 구체적인 작업 | 결과물·종료 조건 |
|---|---|---|
| 1 | 대응표 상세 구조 작성 및 전체 업무 배정 | 68개 컨트롤러 전부에 단계·작업 ID 연결, 화면/SQL 전용 기능 별도 목록 |
| 2 | 사용자·사업소·조직 원본 필드와 관리 범위 분석 | 필드·참조·조직 이동·동시 수정의 차이표 |
| 3 | 권한 신청·심사·위임·회수 원본 이력 분석 | 상태 전이·최신 이력·기간·원자성 시나리오 |
| 4 | 사용자·권한 저장 계약 및 변경 설계 | 키·이력·버전·트랜잭션과 기존 저장 호환 방안 |
| 5 | 분석된 차이를 작은 기능 단위로 구현 | API·서비스·저장소·화면이 함께 동작하는 변경 묶음 |
| 6 | 권한·사용자 통합 검증 및 진척 갱신 | 테스트 결과, 화면 증적, 대응표·현황 갱신 |

첫 묶음의 실제 분석·구현 소요와 발견된 기능 수를 기준으로 후속 일정과 작업 크기를 추정한다. 현재는 인력·세부 기능 수·시험 환경 제공일이 확정되지 않아 날짜별 납기나 전체 공수를 고정하지 않는다.

## 5. 진척 관리와 완료 근거

기능 대응표에는 최소한 다음 항목을 둔다.

`feature_id`, 업무명, 우선순위, 원본 화면/이벤트, 원본 API/메서드, 원본 SQL/공통 함수, 입력·조회·검증·부수 효과, 대상 화면/API/서비스/저장소, 선행 기능, 상태, 남은 차이, 검증 시나리오, 검증 근거/일자/대상 커밋, 외부 조건.

| 상태 | 판정 기준 |
|---|---|
| NOT_ANALYZED | 조사 목록만 있고 상세 동작 분석 전 |
| ANALYZED | 원본 규칙·차이·대상·검증 시나리오 식별 |
| IMPLEMENTING | 해당 기능의 구현 진행 중 |
| READY_TO_VERIFY | 구현 완료, 필요한 검증 미완료 |
| WAITING_EXTERNAL | 시험 환경·외부 규격 등 필요한 조건 대기; 내부 검증 결과는 별도 보존 |
| VERIFIED | 해당 기능의 원본 규칙과 필요한 화면·저장·연계 검증을 모두 통과 |

기능별 완료에는 다음 근거가 필요하다.

- 원본 출처와 대상 구현 연결, 입력·검색·상태 전이·부수 효과의 비교 결과.
- 정상 흐름과 해당 기능에 필요한 권한 거부·경계값·동시 변경·실패 복구 검증.
- 저장 기능은 재시작 유지와 트랜잭션 결과, 화면 기능은 실제 조작 결과.
- 외부 연계 기능은 실제 시험 환경의 요청·결과·실패 시나리오 증적.
- 최신 대상 커밋과 검증 결과. 이후 관련 규칙이 변경되면 영향받는 완료 판정을 재검토.

진척 보고에는 업무별 분석·구현·검증 완료 수, 새로 발견된 범위, 남은 차이, 외부 대기 조건, 다음 작업을 포함한다. 기능 분모가 바뀌면 이유를 함께 기록한다. 컨트롤러는 연결된 하위 기능이 모두 검증된 경우에만 완료로 집계한다.
