# 2단계 권한 분류·연결 이관 계약

## 원본과 입력 형식

- 분류 원본은 `TN_CM_AUTH_CLSF_BASIC`, 권한 연결 원본은 `TN_CM_AUTH_BASIC.AUTH_CLSF_ID`다.
- [export_authority_classification_tree_ai_ab_cy.sql](sql/export_authority_classification_tree_ai_ab_cy.sql)은 데이터를 변경하지 않는 두 개의 조회 결과 집합을 반환한다.
- 첫 번째 결과 집합을 `classifications`, 두 번째 결과 집합을 `authorityLinks` 배열로 내보내 다음 하나의 JSON 객체로 결합한다.
- 원본 `AUTH_CLSF_ID`가 `NULL`인 미분류 권한은 1단계 권한 마스터의 nullable 값으로 그대로 보존하며 `authorityLinks` 결과에서는 제외한다.

```text
{
  "classifications": [원본 분류 조회 결과],
  "authorityLinks": [원본 권한 연결 조회 결과]
}
```

실제 행은 승인된 원본 조회 결과만 사용한다. 분류 ID, 명칭, 상위 관계, 사용 여부 또는 권한 연결을 코드·화면 문구로 추정해 채우지 않는다.

## 실행 순서

1. 승인된 원본 조회 환경에서 SQL을 읽기 전용으로 실행한다.
2. 두 결과 집합의 건수와 `AI`, `AB`, `CY`, `MO` 시스템 범위를 원본 담당자가 검토한다.
3. 결과 컬럼 별칭을 JSON 키로 유지해 하나의 객체로 결합한다. `UPPER_AUTH_CLSF_ID`가 없는 값은 `null`로 보존한다.
4. `/authority-requests.html`의 권한 분류 관리에서 JSON 파일을 선택한다.
5. 화면에 표시된 분류·권한 연결의 시스템별 건수와 실제 파일의 일부 형식을 확인한다.
6. `AUTHORITY_UPDATE` 권한이 있는 관리자가 이관 버튼을 눌러 `POST /api/admin/authority-classifications/import`를 실행한다.
7. 성공 후 화면이 분류 목록과 권한 신청 옵션을 다시 조회한 결과를 확인한다.

## 처리 원칙

- 파일 선택과 미리보기는 저장 작업이 아니다.
- 서버는 전체 분류와 연결을 검증한 뒤 한 작업으로 반영해야 한다. 한 행이라도 잘못되면 부분 반영하지 않는다.
- `authClsfId`, `upperAuthClsfId`, `authClsfNm`, `useFlag`, `authId`는 원본 값을 자르거나 바꾸지 않는다.
- 상위 분류가 없다는 사실과 알 수 없다는 사실을 구분한다. 승인 추출에서 확인된 DB `NULL`만 JSON `null`로 전달한다.
- 1단계에서 존재하는 대상 권한에 대해서만 분류 연결을 반영한다. 누락된 권한을 가짜 이름으로 생성하지 않는다.
- 이 파일과 화면에는 원본 분류의 seed 또는 예시 가짜 행을 두지 않는다.

## 서버 검증 규칙

- 분류 ID와 상위 분류 ID는 `AI`, `AB`, `CY`, `MO` 중 하나와 숫자 4자리로 구성된 6자리 값이다.
- 권한 ID는 같은 시스템 코드와 숫자 10자리로 구성된 12자리 값이며 1단계에서 먼저 존재해야 한다.
- 분류명은 공백 문자를 임의로 제거하지 않으며 필수·최대 100자다. 사용 여부는 `Y` 또는 `N`이다.
- 부모와 자식, 권한과 분류는 같은 시스템이어야 한다. 고아 부모, 순환, 중복 분류와 중복 권한 연결은 전체 요청을 실패시킨다.
- 원본에서 비활성 분류 아래 하위 분류나 권한 연결이 남아 있는 경우 관계와 사용 여부를 그대로 보존한다.
- 입력하지 않은 기존 분류와 권한 연결은 삭제하지 않는다. 같은 자료를 다시 실행하면 권한 버전도 증가하지 않는다.
