# P1 이력별 SSO 연결·과거 기록 통합 조회

2026-09-03. `6da19e5` 이후 작업 트리 기준. 두 서브에이전트가 SSO 이력 연결·조건 조회와 과거 이력 읽기 모델을 나누어 구현했다. 주 에이전트는 자동 기록 연결, 관리·이력 화면, 인증 경계, 파일 DB 복원·롤백을 통합했다. 원본 `C:\arisuinfo`는 읽기만 했고 원본 DB에는 접속하지 않았다.

## 구현 범위

| 기능 | 변경 |
|---|---|
| 이력별 SSO소속 | 실제 직접 권한 이력의 사용자·조직·권한·유형·순번에 당시 SSO사업소·부서·등록시각 연결 |
| 신규 자동 기록 | 명시적 소속이 있는 신청·관리자 직접 부여 시 연결 생성. 승인·반려는 원래 신청의 연결, 회수는 직전 권한 이력의 연결 승계 |
| 이전 이력 연결 | 관리자 API와 ‘권한 이력 SSO 연결’ 화면에서 확인된 당시 소속·시각만 등록. 이력 존재·활성 대응표·버전 검사 |
| 담당자 조건 조회 | 현재 SSO사업소·부서에 연결된 직접 이력 중 권한별 최신 건 존재 검사. 권한 ID·처리상태·시스템 접두어 필터 |
| 사업소 보정 | 요청 사업소 `100`을 `200`으로 변환한 후 기존 본부/사업소 범위 검사 |
| 과거 기록 통합 | 신규 처리 기록, 기존 신청, 권한 기록을 읽기 전용으로 결합. 명시적 연결 키로만 중복 제거 |
| 이력 화면 | 출처·현재 사용자명·권한명·처리자명 표시. 시각·기간·사유가 없으면 ‘확인 불가’ 표시 |

소속이 없는 시점의 신청에 나중의 소속을 덧붙이지 않는다. 신청 뒤 사용자가 이동해도 후속 처리 연결에는 신청 당시 소속을 유지한다. 기존 사용자·권한의 `organizationId`를 일괄 변경하지 않는다. 위임 기록은 통합 이력에 구분해서 표시하지만 원본 직접 권한의 담당자 조회 조건에는 포함하지 않는다.

## 원본 근거와 조회 순서

- `src/main/resources/mappers/arisuinfo/cm/usr/usrMngMapper.xml:167–205`: 현재 사용자와 같은 SSO사업소·부서의 직접 이력을 선택 → 권한별 `REG_DT DESC, AUTH_APLY_SEQ DESC` 최신 건 → 처리상태·권한 ID 조건. 권한 기본정보는 존재해야 하지만 활성 여부·유효기간은 조회 조건이 아니다.
- `src/main/java/arisuinfo/cm/usr/service/impl/UsrMngServiceImpl.java:129,160`: 요청의 `100→200` 변환 뒤 서버 소속 범위 검사. 저장된 사업소코드를 바꾸는 규칙이 아니다.
- `src/main/resources/mappers/arisuinfo/cm/auth/auth/authUsrMapper.xml:160–219`: 사용자 전 조직의 직접 이력 조회, 현재 사용자·권한·처리자 명칭 결합.
- 같은 mapper `368–425`, 서비스 `342–349,451`: 승인 선택 행의 SSO소속을 처리 이력에 유지한다.
- 같은 mapper `826–853`: 로그인 권한은 현재 세션의 SSO사업소·부서로 제한한다. 이 마지막 인가 전환은 이번 범위에 포함하지 않았다.

담당자 조회는 유효 권한 보유자 목록과 다르다. 최신 반려·회수·만료 기록도 조건에 따라 조회된다. 최신 승인만 미리 걸러서 과거 승인을 다시 나타내지 않는다. 기존 미연결 이력은 당시 조직·시각을 알 수 없으므로 이 조건 조회에서 제외한다.

## 저장·API 계약

새 저장 키 `authority-sso-history-links`, `StoredState(links)`를 추가했다. 연결 키는 `(username, organizationId, authorityId, assignmentType, assignmentSequence)`이며 SSO 두 코드, `registeredAt`, 버전을 보존한다. 이전 저장소에 키가 없으면 빈 상태로 시작한다. 확인된 과거 연결을 수정할 때는 `expectedVersion`이 일치해야 한다.

- `GET/POST /api/admin/authority-sso-history-links`: 권한 관리 조회/수정 인가 적용.
- `GET /api/colleagues`: 기존 독립 `DIRECTORY_LOOKUP` 인가 유지. `authId`, `procStatus`, `systemPrefix` 선택 조건 추가.
- `GET /api/me/authority-history/full`: 인증한 본인만 조회. 요청의 username으로 다른 사용자를 고를 수 없다.
- `GET /api/admin/authority-history/full`: 관리 조회 인가와 사용자·상태 조건.
- 기존 `/authority-history` API 및 journal 저장 형식은 유지한다.

전체 이력은 저장 데이터를 백필하지 않는다. journal과 신청은 사용자·조직·권한·유형·신청번호·상태, journal과 실제 권한 이력은 사용자·조직·권한·유형·순번·상태로 연결한다. v2 대기 신청은 저장된 baseline으로 실제 PENDING 행을 연결할 수 있다. 완료 요청에 연결 근거가 없으면 유사한 기간이나 이름만으로 같은 승인이라고 합치지 않는다.

따라서 전체 건수는 **출처별 기록 수**다. 완료된 v2 요청에서 복원한 신청 당시 기간, 과거 직접 부여의 처리 시각·사유처럼 저장돼 있지 않은 값은 null이다. 알려진 등록시각을 먼저 역순으로 표시하고 시각 불명 기록은 뒤에 안정적으로 정렬한다. 원본에 없는 로컬 위임·legacy 기록까지 표시하는 확장 조회이므로 Oracle 이력 화면과의 전체 동등성 완료로 판단하지 않는다.

## 검증 기록

- 자동 테스트 **126개 통과**, 실패·오류·건너뜀 없음. 이전 109개 대비 통합 이력 5개, 이력 연결 6개, 자동 연결 통합 3개, 전체 이력 API 2개, 연결 관리 API 1개 추가.
- 원본 최신 판정 순서, 현재 SSO와 다른 조직·미연결·위임 이력 제외, 비활성 권한/만료 이력 포함, 이름·부서·권한·상태·접두어 조건, `100→200` 후 범위 검사.
- 조직 이동 뒤 반려·회수의 이전 SSO 연결 계승, 나중의 소속으로 과거 미연결 신청을 보정하지 않음, 신규 관리자 직접 부여 자동 연결.
- 전체 이력 API 본인 범위와 관리자 인가, 현재 이름 반영, 요청/직접/위임 기록의 명시 키 중복 제거, 연결 불명 값 보존.
- 파일 DB 재개방 후 연결과 통합 조회 결과 유지. 실패 시 SSO 연결·신청·journal·DB·revision 동시 롤백. 통합 조회 전후 저장 내용·revision 불변.
- 별도 18081 메모리 서버에서 이전 권한의 출처·‘확인 불가’ 표시, 사용자 조건 조회, 신규 직접 부여의 journal/assignment 중복 제거, 관리자 이력 SSO 연결 저장, 담당자의 권한·승인 상태·접두어 복합 조회와 반려 조건의 빈 결과를 확인했다.
- JavaScript 구문, 변경 공백, UTF-8 디코딩·대체 문자, 기능 대응표 대상 경로 검증 통과.
- 검증 탭과 18081 서버는 종료했다. 기존 8080 서버는 재시작하지 않았으며 로그인 응답 200을 확인했다.

## 다음 우선순위와 남은 차이

1. **SSO 인가 전환**: 현재 로그인 권한과 신청 중복·CHANGE 회수는 기존 로컬 조직 ID를 사용한다. SSO A→B 이동 뒤 로컬 조직 ID가 같으면 A 권한을 B에서도 유효하게 보는 차이가 남아 있다. 이력 연결과 조회 완료를 인가 전환 완료로 보고하지 않는다.
2. 현재의 사용자·로컬 조직·권한별 순번과 원본 전역 신청순번·등록일 정렬 차이를 해소한다. 원본 자료 없는 과거 이력은 미연결·시각 불명으로 남긴다.
3. 반려·회수 사유 정정, 관리자 직접 재부여의 현재 유효 승인 차단, 개별 회수 사유·종료일 규칙을 보완한다.
4. 실제 SSO 인증, 별도 SSO사업소·부서 명칭 이력 표시, AI/AB 연계 권한, Oracle 및 운영 데이터 동등성 검증은 남아 있다.
